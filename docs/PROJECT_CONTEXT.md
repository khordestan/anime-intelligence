# Anime Intelligence — project context

Last updated: 2026-11-15. GitHub `main` is the source of truth. Update this document alongside implementation changes; use Git history and Actions for exact commit and validation status. This file contains no real user data or operational credentials.

## Goal and working agreement

Build a detailed, current anime catalog with personal tracking, explainable taste intelligence, and new episode/season alerts. Develop autonomously with actual code, tests and commits. Keep the repository public, fix failing checks before moving on, and do not deploy publicly before authentication, isolation and production security are ready. A ChatGPT Project may point here; it must not become a competing copy of implementation state.

## Current architecture

| Area | Implementation and boundary |
| --- | --- |
| API | Go 1.26 modular monolith, versioned REST under `/api/v1`; `cmd/api`, `internal/httpapi`, domain handlers in `internal/modules` |
| Persistence | Request-aware `store.Repository`; PostgreSQL via pgx for multi-user runtime, JSON file only for single-user local development |
| Database | Embedded checksummed transactional migrations `000001`–`000011`; advisory migration lock; separate administrator and restricted runtime roles |
| Identity | Argon2id passwords; random opaque bearer sessions; database stores digests; transaction-local identity and forced RLS on thirteen private tables |
| Dashboard | Next.js 16 / React; in-memory bearer/proof handling, cancellation and account-revision checks prevent stale responses crossing accounts |
| Mail | Optional certificate-verified implicit-TLS SMTP; AES-256-GCM encrypted PostgreSQL request inbox and mail outbox; admission commits before HTTP 202; leased workers with bounded persisted retries |
| Worker | `cmd/worker` is a lifecycle placeholder; the API currently owns identity delivery; no durable scheduler/provider sync exists |
| Intelligence | Deterministic, explainable pure-Go Personal Match core with tests; recommendation HTTP serving is pending |

PostgreSQL is selected by `DATABASE_URL`; connection/schema/security failures stop startup without falling back to JSON. Provision with `cmd/migrate` and `deployments/runtime-role.sql`. See [runtime guide](POSTGRES_RUNTIME.md), [architecture](ARCHITECTURE.md), [security contract](IDENTITY_SECURITY.md), and [roadmap](ROADMAP.md).

## Key decisions and security constraints

- Never trust request-supplied user IDs. Resolve a bearer digest, acquire account state before session/proof rows, recheck credentials under locks, then run owner-scoped queries with transaction-local RLS context. RLS supplements application authorization.
- API database role must not own tables or have elevated privileges/BYPASSRLS. Migrations use separate credentials. Require migration 000010 at startup; prior inbox/outbox deployments must already have current runtime-role grants.
- Sessions expire after 24 hours. Refresh changes the digest in the same row, preventing remote-revocation races. Password change/reset revokes all sessions; account deletion cascades private records.
- Only explicit bearer headers are supported; cookies/CSRF handling are not implemented. Browser reload drops the credential. Never persist credentials in browser storage.
- Unverified users retain account/recovery/export/deletion access; reset and refresh do not establish email ownership. Mail-disabled installations cannot unlock new accounts' product access.
- Recovery/verification proofs are random, purpose/address-bound, expiring and single use. Challenge records hold digests; a separate encrypted outbox temporarily holds the delivery envelope, including the proof, encrypted with a deployment key held outside PostgreSQL. Reset lasts thirty minutes; verification one hour. Mail links use fragments, scrubbed immediately, and explicit POST confirmation. Issuance has one-minute cooldown/five-per-hour quotas.
- Retries resend the same message without reissuing or consuming additional issuance quota. All errors/logs must redact provider responses, recipients and secrets. SMTP DATA acceptance ends retries; failed QUIT does not cause another send. Ambiguous network failures can still duplicate a message.
- Keep real account details, personal watch histories, secrets, database dumps and real credential hashes out of this public repository. Use synthetic fixtures only. Do not add personal preferences from chat to seed data.

Outbox claims use account → challenge → outbox lock ordering and release all database locks before SMTP. One-minute leases carry random hashed credentials; stale acknowledgements cannot complete a newer claim. Retry delays are 30/60/120/240 seconds, capped at five claims including crashes. Success, exhaustion, expiry or invalidation erases ciphertext; completed metadata is removed after one day when workers run. HTTP/export never exposes outbox rows.

Request intake uses a separate forced-RLS inbox and trusted `app.identity_request_worker` context, reset on every transaction. Payloads are padded to a fixed 540-byte ciphertext; reset intents contain submitted email, verification intents contain only a session digest, never raw bearer tokens. Workers revalidate that credential before issuance; logout/refresh/password change/deletion can invalidate queued verification. Request leases last one minute, with five claims and 5/10/20/40-second backoff. Payloads are erased on completion/expiry/exhaustion; completed metadata is purged after one day. Configured runtime has no volatile fallback.

## Known issues and next priorities

1. **Queue monitoring and key operations:** request admission now persists a fixed-size encrypted intent before HTTP 202 without looking up an account. Processing atomically commits inbox completion, challenge issuance and encrypted mail. Requests expire after fifteen minutes; capacity is 256 active intents shared across instances. `cmd/identity-status` now reports queue counts, leases, cleanup needs and age from a read-only snapshot without private data; see [queue operations](IDENTITY_QUEUE_OPERATIONS.md). Retained terminal outcomes now distinguish request issuance/no-action and mail acceptance/invalidation/expiry/exhaustion without private reason strings. `-format=prometheus` exports a fixed set of aggregate gauges for a trusted textfile collector; JSON remains default and no HTTP endpoint is added. Atomic `-output-file` snapshots, disabled systemd/Prometheus examples and promtool-tested alert rules are available in [monitoring setup](../deployments/monitoring/README.md). Host activation, target inventory, receiver routing and broader provider telemetry remain pending. `MAIL_OUTBOX_KEY` encrypts new work; optional `MAIL_OUTBOX_PREVIOUS_KEYS` accepts up to three distinct decryption keys. Follow the staged reader/writer rollout and retirement procedure in [key rotation](IDENTITY_KEY_ROTATION.md); automated secret distribution and rotation are not implemented. The [synthetic logical recovery drill](BACKUP_RECOVERY.md) covers restore fidelity, compatible/missing queue keys and an offline credential fence; real backup/key distribution and recovery remain operational work. Protect keys separately from database backups. Wrong keys/corrupt envelopes preserve ciphertext and fail closed but can block the oldest pending job until corrected or expired. SMTP remains at-least-once; ambiguous failures may duplicate mail.
2. **Production abuse controls:** add reviewed ingress/distributed source throttling and monitoring. The process-wide password gate bounds hashing, but can be exhausted; per-account locks can deny service to known addresses. Do not treat these as complete public-ingress protection.
3. **Operations:** `/healthz` is liveness; `/readyz` is an uncached two-second readiness check with at most one database probe in flight per handler. PostgreSQL readiness rechecks the live restricted role, thirteen forced-RLS tables and required security columns, reusing startup validation. It does not certify policy correctness, SMTP or production readiness. Both routers now set `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` at the outer response boundary, including errors/redirects/preflights; existing protected-handler no-store remains. Public catalog caching is intentionally disabled too. Request logs now contain matched route templates and bounded method values, never raw request paths. Further health/queue/security telemetry, expired-session/proof cleanup, real backup storage/PITR and measured recovery objectives, TLS/ingress and mail runbooks, load/reliability testing and independent security review. No public deployment is authorized yet.
4. **Historical recovery boundary:** the new [backup recovery guide](BACKUP_RECOVERY.md) and opt-in `TEST_POSTGRES_RECOVERY=1` CI drill use only disposable synthetic databases and real PostgreSQL 17 dump/restore clients. Archives exclude ownership/ACLs; restore validates migration checksums, reapplies reviewed restricted-role grants and tests all private-table RLS. `deployments/recovery-fence.sql` is manual/offline administrator-only work, never a migration: atomically force fresh password resets, revoke sessions/proofs and erase restored queues without their keys. Tests cover injected rollback, repeatability and fresh recovery. Fencing cannot identify accounts deleted or changed after the snapshot; independently protected deletion/address/security-event reconciliation is required before even recovery intake reopens. The application does not maintain that inventory. No real backups, SMTP delivery or host activation are performed.
5. **Tracker removal:** `DELETE /api/v1/tracker/{id}` removes only the owner's entry and its title ratings/progress atomically; verified email is required in PostgreSQL. Foreign/missing/repeated IDs return the same 404. JSON removal restores memory on persistence failure. Reapply `deployments/runtime-role.sql` for the new DELETE grants on user_anime/watch_progress/user_ratings before updating existing runtimes; no schema migration is needed. Dashboard removal controls now require explicit confirmation, explain ratings/progress loss, retain the entry on errors, and reset confirmation on account changes. Account/reload revisions fence late mutation results and overlapping refreshes.
6. **Product delivery:** provider capability/license review and adapters, season/episode relations and freshness, tracking completeness, then release alerts and explainable recommendation serving. Preserve provenance and spoiler scope.
