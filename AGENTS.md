## Architecture and invariants

- Keep the Go API and catalog worker as separate entry points of a modular monolith. `cmd/api` selects the PostgreSQL runtime when `DATABASE_URL` is set. A failed PostgreSQL startup must fail closed. JSON mode is unauthenticated, single-user and loopback-only for development. Preserve existing clients and both runtime modes where applicable.
- Keep HTTP wiring in `internal/httpapi`, domain and ranking logic in `internal/modules`, persistence and operational services in `internal/platform`, and source-specific normalization in `internal/providers`. The Next.js dashboard in `web` calls the versioned REST API. PostgreSQL and pgx are the system of record. Add infrastructure only with a demonstrated need.
- Derive identity from server-verified bearer sessions. Keep explicit owner predicates, verified-email product gates and transaction-local forced RLS. Preserve account-before-session/proof and account/session-before-owner advisory lock ordering. Keep database owner, API runtime, curator, worker and diagnostic grants separate. Never bypass RLS or solve missing grants by elevating the API role.
- Store passwords as Argon2id hashes and persisted bearer/proof verification material as digests. Keep delivery payloads encrypted. Keep bearer/proof values out of logs and persistent browser storage. Preserve request redaction, account-switch fencing, atomic session operations, encrypted mail queues, and export/deletion coverage for private data.
- Keep catalog identities canonical and source mappings exact. Preserve provenance, attribution, explicit approval, idempotency, schedule versus availability distinctions, and transactional preview/import semantics. Keep source adapters opt-in and spoiler-sensitive evidence hidden by default. AI is a hybrid target. Deterministic evidence and typed, authorized tools constrain future model integration.
- Keep the repository public and fixtures synthetic. Do not commit credentials, private configuration, real account details, personal watch histories, dumps or unapproved provider material. Public deployment, live provider activation and real notification delivery require explicit authorization and applicable readiness or approval gates.

## Code and checks

- Reuse existing transaction, validation and transport patterns. Write readable Go and TypeScript, format changed Go files with `gofmt`, keep strict TypeScript types, and make retries, concurrent writes and partial failures safe. Prefer focused change sets and backwards-compatible contracts.
- Never edit an applied migration. Add paired numbered SQL migrations, update grants and startup/readiness checks when the runtime contract changes, and test apply, reapply and rollback on disposable PostgreSQL. Keep migration and runtime credentials separate.
- Update [OpenAPI](api/openapi.yaml) and feature documentation for API changes. Add focused regressions for changed behavior, privileged paths, concurrency or account isolation as appropriate.
- Run `make check` for Go and `npm ci`, `npm test`, `npm run typecheck` and `npm run build` from `web` for web changes. Run `npm run test:e2e` for dashboard behavior changes after installing Playwright Chromium. PostgreSQL integration tests skip without `TEST_DATABASE_URL`. Use a disposable admin connection and the test commands in [README.md](README.md) for changes involving SQL, authorization or migrations. The hosted workflows also verify real browser paths, recovery, monitoring and security.
- Record which checks ran, which were skipped and which hosted run verified the exact change. Fix relevant failures before merging. Use Actions links for hosted results and distinguish them from local runs.

## Autonomous execution

Check branch status, scoped instructions, recent commits and CI, then choose the highest-priority unblocked deliverable. Make code changes, test, commit and push through the available GitHub workflow. Open a PR or update the existing one, wait for required checks where execution allows, diagnose failures, and continue to the next in-scope item. Handle routine technical decisions independently. Ask only when blocked on access, a material product decision, explicit operational authorization or an irreversible action. Honor existing user changes and keep the worktree clean of unrelated edits.

Update [PROGRESS.md](PROGRESS.md) and [ROADMAP.md](ROADMAP.md) when scope or status changes. Record substantive decisions and verification in [project context](docs/PROJECT_CONTEXT.md) or the [implementation log](docs/IMPLEMENTATION_LOG.md) as appropriate. If the session ends with work underway, leave the exact branch or PR, tests and their results, unresolved blocker and next action so the following session can resume.
